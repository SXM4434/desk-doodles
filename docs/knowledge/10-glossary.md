# 10 — The vocabulary: canonical terms ↔ Sebs's words

**In one sentence:** This page is the translation table between the words the codebase and research docs use (the domain canon) and the words you actually think in (your shorthand and your C4D / Substance / Photoshop anchors), so neither vocabulary silently drifts away from the other.

---

## Plain language

Every long project grows two languages. There's the **canon** — the names the code, the locked contract (`09-LOCKED-MODEL.md`), and the research docs use, which have to be precise because functions and invariants hang off them. And there's **your language** — "splinter toggle," "the master dial," "living breathing system" — which is faster, truer to intent, and the one you'll reach for at 1am. The bug this page prevents is the written-vs-intent gap: you say one thing, the doc means another, and a session builds the wrong thing confidently.

How to read the tables:

- **Term** — the canonical name. This is the string you'd grep for.
- **Plain meaning** — what it is, explained through tools you already know (baking, blend modes, layer groups, sweeps, seeds), not through other jargon.
- **Sebs's shorthand / anchor** — your verbatim phrase where one exists *in the record* (quoted, with source), or a **proposed** anchor where it doesn't. Proposed anchors are suggestions, not history — per the vocab protocol, you confirm or replace them.
- **Where it lives** — real file, real line, or real doc section. If something is planned-not-built, the cell says so.

One framing for why translation matters both directions. Canon → you: when a doc says "the Treatment's primary axis," you should be able to read it as "which knob does the heavy lifting for darkness — gap or weight." You → canon: when you say "make the lines splinter more," the session must reach for `jaggedness`, not `wobble`, because those are different fields driving different math. The table IS that mapping, written down.

---

## The design — why it's built this way

**Why three tables instead of one alphabet.** The three domains have different trust levels. Project terms are *ours* — defined by our own contract, so the table is authoritative. Engineering terms are *borrowed CS canon* serving your rebuild — the plain meanings must match what the rest of the world means, and per your vocab protocol the first pass needs your confirmation before it hardens (it's marked accordingly). 3D/graphics terms are *your strongest domain* — there the table mostly maps industry words onto things you already do daily, plus flags where this project bends a term (roughness in I-11 is borrowed FROM PBR, deliberately).

**Why plain meanings use your anchors instead of textbook definitions.** Textbook definitions define jargon with other jargon; that's how rebuild-zone reading stalls. An anchor ("memoization = baking: compute once, reuse, invalidate when the source changes") gives you a thing you can mentally render. The risk — anchors can be lossy — is handled by keeping the canonical term as the row key, so precision is always one grep away.

**Why quoted-vs-proposed is marked explicitly.** The vocab protocol's no-fake-provenance rule. A shorthand column where invented phrases look like your phrases would poison the whole table — you'd stop trusting the quotes that ARE yours. So: quotes with a source are yours; everything else says *proposed*.

**Why a "Where it lives" column at all.** A glossary that can't be verified rots into vibes. Every row points at the code or doc that makes it true, which also makes this page a navigation index: term → file → read the real thing.

**Rejected:** one giant alphabetical table (loses the trust-level distinction); defining terms only by their code types (correct but unreadable for the rebuild purpose); skipping planned-only terms like tone patch (they're in your head and in the docs, so they belong here — just labeled planned).
